# مؤلفه‌ها و پیش‌نیازها

| مؤلفه | کاربرد | نسخه‌ی به‌کاررفته در درستی‌سنجی |
|---|---|---|
| هسته‌ی SwarmOps (`cmd/api`) | سرور: APIها، فروشگاه، کنسول، کارگر فرمان، صورتحساب | ساخته‌شده از شاخه با Go 1.26.6 |
| عامل ماشین (`cmd/agent`) | عملیات Docker و Swarm روی هر گره | همان منبع با نسخه‌ی `v0.22.0` |
| MariaDB یا MySQL | پایگاه داده‌ی کنترل‌گر | MariaDB 11.4.13، MySQL 8.4.11 |
| Docker Engine در حالت Swarm | اجرای دروازه و برنامه‌های مشتری | Docker 29.4.0، تک‌گره |
| Node.js و npm | ساخت برنامه‌های وب | Node.js 26.5.0 |
| Traefik | دروازه، نصب‌شده توسط SwarmOps | v3.6.13 |

: مؤلفه‌ها

پایگاه داده باید MariaDB 11.4 LTS یا MySQL 8.4 LTS یا نسخه‌ای بالاتر از همان سری باشد. ایمیج‌های کانتینر خود SwarmOps برای `amd64` ساخته می‌شوند؛ روی میزبان `arm64` هسته و عامل را مانند محیط درستی‌سنجی به‌صورت باینری بومی اجرا کنید.

# توسعه‌ی محلی

## پایگاه داده

::: ltr
```bash
make dev-db
```
:::

این فرمان کانتینر MariaDB 11.4 با نام `swarmops-mariadb` را روی `127.0.0.1:3307` با گذرواژه‌ی root برابر `devroot` راه می‌اندازد و پایگاه داده‌ی `swarmops` را با `utf8mb4` می‌سازد؛ اجرای دوباره کانتینر موجود را روشن می‌کند. برای آزمودن روی MySQL نیز، سرور دومی مثلاً روی درگاه 3308 راه بیندازید:

::: ltr
```bash
docker run -d --name swarmops-mysql -e MYSQL_ROOT_PASSWORD=devroot -p 127.0.0.1:3308:3306 mysql:8.4
```
:::

## اجرای همه‌چیز

::: ltr
```bash
make local
```
:::

`make local` یک عامل ماشین روی loopback آماده می‌کند، هسته را با احراز هویت توسعه روی `127.0.0.1:8084` اجرا و به عامل وصل می‌کند و سرور توسعه‌ی Vite را روی `127.0.0.1:5284` اجرا می‌کند. وضعیت توسعه زیر `$TMPDIR/swarmops-dev` نگهداری می‌شود (قابل تغییر با `SWARMOPS_DEV_DIR`). اجزا را می‌توان جداگانه با `make dev-agent`، `make dev-api` و `make web-dev` اجرا کرد. کنسول در `http://127.0.0.1:5284/` و فروشگاه در `http://127.0.0.1:5284/store.html` باز می‌شود.

## تنظیمات توسعه

| متغیر | معنا |
|---|---|
| `SWARMOPS_INSECURE_DEV_AUTH=true` | احراز هویت توسعه را فعال می‌کند؛ هرگز در تولید استفاده نشود. |
| `SWARMOPS_DEV_SESSION_KEY` | دست‌کم ۳۲ بایت. کلید رمزنگاری داده از آن مشتق می‌شود؛ آن را میان راه‌اندازی‌ها ثابت نگه دارید، وگرنه ستون‌های محرمانه‌ی پایگاه داده خوانا نخواهند بود. |
| `SWARMOPS_DEV_PASSWORD_HASH` | درهم‌سازی bcrypt گذرواژه‌ی اپراتور توسعه (کاربر `SWARMOPS_ADMIN_USERNAME`، پیش‌فرض `admin`). |
| `SWARMOPS_DEV_DATABASE_DSN` | DSN توسعه؛ پیش‌فرض `root:devroot@tcp(127.0.0.1:3307)/swarmops`. |
| `SWARMOPS_MUTATIONS_ENABLED=true` | تغییرات سرورها و برنامه‌ها، از جمله تأیید سفارش، را مجاز می‌کند. |
| `SWARMOPS_DEV_MACHINE_API_*` | اتصال به عامل ماشین روی loopback (با `make local` تنظیم می‌شود). |

: تنظیمات توسعه

درهم‌سازی گذرواژه را برای نمونه با `htpasswd -nbBC 10 admin 'your-password' | cut -d: -f2` بسازید.

## آزمون‌ها

::: ltr
```bash
go vet ./...
SWARMOPS_TEST_DATABASE_DSN='root:devroot@tcp(127.0.0.1:3307)/' SWARMOPS_TEST_DATABASE_REQUIRED=1 go test ./...
SWARMOPS_TEST_DATABASE_DSN='root:devroot@tcp(127.0.0.1:3308)/' SWARMOPS_TEST_DATABASE_REQUIRED=1 go test ./...
npm --prefix web run typecheck
npm --prefix web test
npm --prefix web run build
make stack-check-all TAG=ci
make docs-check
```
:::

هر آزمون پایگاه داده طرح‌واره‌ی خودش با نام `swarmops_test_…` را می‌سازد و حذف می‌کند. بدون `SWARMOPS_TEST_DATABASE_REQUIRED`، آزمون‌هایی که به پایگاه داده دسترسی ندارند رد (skip) می‌شوند، نه ناموفق.

# ساخت

::: ltr
```bash
npm --prefix web ci
npm --prefix web run build     # writes the storefront and console into internal/web/static
go build -o swarmops-core ./cmd/api
go build -ldflags "-X main.version=v0.22.0" -o swarmops-agent ./cmd/agent
```
:::

ساخت وب باید پیش از `go build` اجرا شود، چون هسته `internal/web/static` را جاسازی می‌کند. بسته‌های انتشار با `scripts/build-release-bundles.sh` تولید می‌شوند که نسخه را مهر می‌زند.

# نصب تولیدی

> گام‌های این فصل از نصب‌کننده و تعریف استک‌های مخزن پیروی می‌کنند و با تولید استک‌ها و بررسی نحوی اسکریپت‌ها بررسی شده‌اند، اما در این پروژه روی سرور Ubuntu **اجرا نشده‌اند** (طرح و گزارش آزمون، بخش ۸).

## آماده‌سازی پایگاه داده

روی سرور پایگاه داده:

::: ltr
```sql
CREATE DATABASE swarmops CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;
CREATE USER 'swarmops'@'10.0.0.%' IDENTIFIED BY 'a-long-random-password';
GRANT ALL PRIVILEGES ON swarmops.* TO 'swarmops'@'10.0.0.%';
```
:::

هسته در راه‌اندازی مهاجرت‌ها را اعمال می‌کند، پس حساب آن به حق ساخت و تغییر جدول نیاز دارد. برای جداسازی سخت‌تر، نخستین راه‌اندازی و هر ارتقا را با حسابی مالک طرح‌واره اجرا کنید و حساب روزمره را به `SELECT`، `INSERT`، `UPDATE` و `DELETE` محدود کنید.

## نوشتن فایل DSN

DSN قالب درایور Go MySQL را دارد:

::: ltr
```text
swarmops:a-long-random-password@tcp(db.internal:3306)/swarmops?tls=true
```
:::

هسته همیشه `parseTime=true`، منطقه‌ی زمانی UTC (`time_zone='+00:00'`)، ترتیب‌بندی `utf8mb4_unicode_ci` و مهلت اتصال ده‌ثانیه‌ای را می‌افزاید؛ نیازی به نوشتن آن‌ها نیست. DSN را در فایلی ذخیره کنید که:

- فایل معمولی باشد، نه پیوند نمادین؛
- فقط مالک بتواند آن را بخواند: هیچ مجوزی برای گروه یا دیگران، مانند حالت `0400` یا `0600`.

در غیر این صورت هسته راه‌اندازی نمی‌شود. همین قواعد برای فایل کلید رمزنگاری داده که دقیقاً ۳۲ بایت در base64 استاندارد است نیز برقرار است.

## نصب صفحه‌ی کنترل

اسکریپت راه‌انداز را با فایل DSN اجرا کنید:

::: ltr
```bash
sudo bash scripts/bootstrap-swarmops-control-plane.sh --database-dsn-file /root/swarmops-database-dsn
```
:::

اسکریپت بدون فایل DSN خوانا و غیرخالی ادامه نمی‌دهد؛ فایل را با نام `database-dsn` در پوشه‌ی پیکربندی هسته نصب و `SWARMOPS_DATABASE_DSN_FILE` را در محیط هسته می‌نویسد. وقتی هسته به‌صورت سرویس Swarm اجرا می‌شود (`deploy/stacks/swarmops.yml`)، DSN به‌صورت راز Swarm با نام `swarmops_database_dsn` داده می‌شود و `scripts/run-swarmops-api.sh` وجود فایل راز را الزامی می‌داند.

## اتصال سرورها و نصب دروازه

1. هر گره را با فرمان نصب **Connect a server** در کنسول ثبت کنید.
2. به مدیری که دروازه را حمل خواهد کرد برچسب `nim.edge=true` بدهید (ترمیم پیش‌نیازها این کار را برای یک مدیر انجام می‌دهد).
3. در *Traffic › Gateway settings* ایمیل تماس ACME و نام میزبان داشبورد را تنظیم کنید؛ در *Traffic › Gateway* پیش‌نیازها را ترمیم و دروازه را نصب کنید (راهنمای کاربر، *آماده‌سازی سکو*).

ترمیم دروازه به عامل ماشین v0.9.3 یا بالاتر نیاز دارد. عامل‌های منتشرشده نسخه دارند؛ عاملی که بدون `-ldflags "-X main.version=…"` از منبع ساخته شود `dev` گزارش می‌دهد و رد می‌شود (طرح و گزارش آزمون، نقص D-6).

## بررسی آمادگی

::: ltr
```bash
curl -fsS https://core.example.com/readyz
```
:::

`/readyz` وقتی دفتر ممیزی و مخزن فرمان — هر دو در پایگاه داده — در دسترس باشند `{"status":"ready"}` و در غیر این صورت ۵۰۳ پاسخ می‌دهد. آن را بررسی سلامت هر متعادل‌کننده‌ی بار یا ناظری جلوی هسته قرار دهید.

# ارتقای یک نصب موجود SwarmOps

نسخه‌های SwarmOps پیش از این پروژه وضعیت را در فایل‌های رمزشده‌ی `.sealed` پوشه‌ی داده نگه می‌داشتند. برای انتقال آن به پایگاه داده:

1. **پشتیبان** پوشه‌ی داده (شامل `commands/`) و کلید رمزنگاری داده را بگیرید.
2. **هسته را متوقف کنید.** دو فرایند نباید یک وضعیت را بنویسند.
3. **پیکربندی:** فایل DSN را مانند بخش ۴.۲ تنظیم کنید.
4. **وارد کردن** با همان محیط هسته (همان پوشه‌ی داده و کلید):

   ::: ltr
   ```bash
   swarmops-core migrate-state
   ```
   :::

   فرمان طرح‌واره را می‌سازد یا ارتقا می‌دهد، هر مخزن را در تراکنش خودش وارد می‌کند و برای هر مخزن یک خط چاپ می‌کند، مانند `imported server profiles and retained keys    1 profiles, 1 keys` و در پایان `controller database is at schema version 9; the sealed files in … are unchanged`. مخزنی که فایل ندارد چیزی وارد نمی‌کند.
5. **درستی‌سنجی:** شمارش‌ها را با آنچه نصب قدیمی نشان می‌داد (سرورها، برنامه‌ها، ورودی‌های ممیزی، اجراها) مقایسه کنید.
6. **هسته را راه بیندازید.** اکنون فقط از پایگاه داده می‌خواند و در آن می‌نویسد.

وارد کردن فایل‌های `.sealed` را تغییر نمی‌دهد و اجرای دوباره‌ی آن تکراری ایجاد نمی‌کند. برای بازگشت، هسته را متوقف و نسخه‌ی قبلی را با پوشه‌ی داده‌ی دست‌نخورده‌اش راه‌اندازی کنید.

# بهره‌برداری

## کار پس‌زمینه

فقط روی هسته‌ی **فعال**، کارگر فرمان هر ۲۵۰ میلی‌ثانیه فرمان‌های سررسیده را بررسی و هر بار یکی را اجرا می‌کند و صورتحساب هر پنج دقیقه ساعت‌های گذشته را حساب و فاکتورهای ماه قبل را صادر می‌کند. هسته‌ی آماده‌به‌کار خواندن‌ها را پاسخ می‌دهد، تغییرات را با ۴۰۹ رد می‌کند و هیچ‌یک از این دو کار را انجام نمی‌دهد.

## پشتیبان‌گیری

::: ltr
```bash
mysqldump --single-transaction --routines --triggers \
  --host=db.internal --user=swarmops --password swarmops > swarmops-$(date -u +%Y%m%dT%H%MZ).sql
```
:::

`--single-transaction` بدون متوقف کردن هسته تصویری سازگار از جدول‌های InnoDB می‌گیرد. هر پشتیبان را همراه نسخه‌ای جداگانه و محافظت‌شده از کلید رمزنگاری داده نگهداری کنید: رازهای درون پشتیبان بدون کلید خوانا نیستند و کلید در پایگاه داده نیست. اگر مصنوعات ساخت باید باقی بمانند، از پوشه‌ی `commands/` داده نیز پشتیبان بگیرید.

## بازیابی

1. هسته را متوقف کنید.
2. پایگاه داده‌ای خالی بسازید و خروجی را بارگذاری کنید: `mysql swarmops < swarmops-….sql`.
3. هسته را با **همان** کلید رمزنگاری داده راه بیندازید. اجراکننده‌ی مهاجرت جمع‌آزماهای ثبت‌شده را بررسی، مهاجرت‌های جدیدتر را اعمال و پایگاه داده‌ای جدیدتر از باینری را رد می‌کند.

## پایش

- **گزارش‌ها (logs):** هسته گزارش‌های ساختاریافته‌ی JSON در خروجی استاندارد می‌نویسد؛ فرمان ناموفق با `command execution failed` همراه شناسه، کنش، سرور، هدف، تلاش و علت ثبت می‌شود.
- **اجراها:** *Activity › Runs* در کنسول گام‌ها، تلاش‌ها و خلاصه‌ی شکست هر فرمان را نشان می‌دهد.
- **ممیزی:** دفتر ممیزی ثبت می‌کند چه کسی چه کرد، شامل هر تصمیم مدیر و رویداد خرید مشتری.
- **پول:** بررسی دفتر کل را به‌طور دوره‌ای اجرا کنید؛ نباید سطری برگرداند:

  ::: ltr
  ```sql
  SELECT w.user_id, w.balance_rial, COALESCE(SUM(t.amount_rial), 0) AS ledger_sum
  FROM wallets w LEFT JOIN wallet_transactions t ON t.user_id = w.user_id
  GROUP BY w.user_id, w.balance_rial
  HAVING w.balance_rial <> COALESCE(SUM(t.amount_rial), 0);
  ```
  :::

## عیب‌یابی

| نشانه | علت محتمل | اقدام |
|---|---|---|
| هسته با *… must be readable only by its owner* خارج می‌شود | مجوز فایل DSN یا کلید بیش از حد باز است. | `chmod 0400` روی فایل. |
| هسته پس از خطای جمع‌آزمای مهاجرت خارج می‌شود | فایل مهاجرتی که اعمال شده تغییر کرده است. | هرگز مهاجرت اعمال‌شده را ویرایش نکنید؛ مهاجرت جدید بیفزایید. |
| هسته پایگاه داده‌ای *newer than the controller* را رد می‌کند | نسخه‌ی جدیدتری این پایگاه داده را مهاجرت داده است. | همان نسخه را اجرا کنید یا پشتیبان پیش از ارتقا را بازیابی کنید. |
| همه‌ی استقرارها با `gateway_required` شکست می‌خورند | دروازه‌ی مدیریت‌شده نصب نیست. | آن را نصب کنید (بخش ۴.۴). |
| استقرار دقیقه‌ها *provisioning* می‌ماند و سپس شکست می‌خورد | بررسی سلامت برنامه هرگز موفق نمی‌شود؛ در این مدت صف مسدود است. | بررسی کنید ایمیج روی درگاهش به `GET /healthz` پاسخ دهد و `wget` یا `curl` داشته باشد. |
| تأیید سفارش با *not connected to a Swarm manager* پاسخ می‌دهد | سرور انتخاب‌شده آفلاین یا غیرمدیر است. | عامل را دوباره وصل کنید؛ `docker info` را روی گره بررسی کنید. |
| تغییرات ۴۰۹ *standby* پاسخ می‌دهند | این هسته هسته‌ی فعال نیست. | از هسته‌ی فعال استفاده یا این هسته را ارتقا دهید. |
| تغییرات ۴۰۳ *Remote mutations are disabled* پاسخ می‌دهند | تغییرات خاموش‌اند. | تغییرات را در پیکربندی هسته فعال کنید. |
| `/readyz` پاسخ ۵۰۳ می‌دهد | پایگاه داده در دسترس یا قابل نوشتن نیست. | سرور پایگاه داده و DSN را بررسی کنید. |

: عیب‌یابی

# فهرست بررسی امنیت

- فایل‌های DSN و کلید فایل معمولی‌اند و فقط کاربر هسته آن‌ها را می‌خواند.
- پایگاه داده فقط از میزبان کنترل و از طریق TLS (`tls=true` در DSN) در دسترس است.
- `SWARMOPS_INSECURE_DEV_AUTH` در تولید تنظیم نشده و کوکی امن (HTTPS) فعال است.
- از کلید رمزنگاری داده جدا از پشتیبان‌های پایگاه داده پشتیبان گرفته شده است.
- کنسول فقط برای مدیران و فروشگاه از طریق HTTPS در دسترس است.
- هر مدیر حساب خودش را دارد تا دفتر ممیزی او را نام ببرد.
